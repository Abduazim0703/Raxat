# Rahat backend

Рабочий сервер для платформы заказа кафе «Рахат»: меню, заказы, комиссия считается
на сервере (а не в браузере — это важно, чтобы никто не мог подделать цену), три
отдельных API для трёх ролей: гость, официант/кухня, владелец.

## Три приложения на одном сервере

- `/` — меню и заказ, для гостей за столом (то, что на NFC-карточке)
- `/staff` — активные заказы и их статус, для официанта/кухни
- `/owner` — выручка и комиссия, для владельца

Все три страницы лежат в папке `public/` и раздаются прямо этим же сервером —
отдельно хостить их не нужно, один деплой закрывает всё.

У каждой роли свой ключ доступа — гость видит только меню и создаёт заказы, официант
не видит выручку и комиссию, владелец видит всё.

## Что это умеет прямо сейчас

**Гостю (публичные эндпоинты):**
- `GET /api/menu` — актуальное меню, включая флаг `inStock` (блюдо закончилось)
- `POST /api/orders` — создать заказ. Обязательные поля: `dineType` (`dine_in` / `takeaway`)
  и `paymentMethod` (`sbp` / `cash`). Цену и комиссию сервер считает сам по своей базе,
  а блюдо «нет в наличии» просто не даст заказать (ответ 409)
- `POST /api/orders/:orderNumber/confirm-payment` — подтверждение оплаты по СБП
  (см. «Что нужно доделать» — сейчас это заглушка вместо реального банковского вебхука)
- `POST /api/waiter-calls` — гость нажал «Позвать официанта»

**Официанту / кухне (ключ `STAFF_API_KEY`):**
- `GET /api/staff/orders` — активные заказы (`awaiting_cash`, `paid`, `preparing`, `ready`)
- `POST /api/staff/orders/:orderNumber/advance` — продвинуть по цепочке
  paid → preparing → ready → served
- `POST /api/staff/orders/:orderNumber/confirm-cash` — официант получил наличные;
  только после этого наличный заказ считается оплаченным
- `GET /api/staff/calls` и `POST /api/staff/calls/:id/resolve` — вызовы гостей
- `GET /api/staff/menu` и `POST /api/staff/menu/:id/stock` — отметить, что блюдо
  закончилось или снова появилось (быстрое действие в смену, права владельца не нужны)
- `PUT /api/staff/menu/:id` — поменять цену, состав, вес, калорийность, фото у блюда
- `POST /api/staff/menu` — добавить новое блюдо в меню (id генерируется из названия)
- `POST /api/staff/upload` — загрузить фото блюда файлом (из галереи/камеры телефона).
  Принимает `multipart/form-data` с полем `photo`, отдаёт `{ url }` — эту ссылку дальше
  передают в `imageUrl` при создании/редактировании блюда. Файлы лежат в папке `uploads/`
  рядом с бэкендом и раздаются статически по `/uploads/...`. Лимит 8 МБ, только
  JPEG/PNG/WEBP/GIF.

**Важно:** ключ `OWNER_API_KEY` тоже принимается везде, где принимается `STAFF_API_KEY` —
поэтому у владельца на `/owner` ровно те же возможности редактирования меню
(цена, фото, наличие, добавление блюд), что и у официанта, без дублирования кода на
бэкенде.

**Владельцу (ключ `OWNER_API_KEY`):**
- `GET /api/owner/summary` — оборот, комиссия, средний чек и **отдельно наличные и СБП**
  (для сверки, сколько наличных должны сдать официанты). Выручка считается по факту
  оплаты, а не по текущему статусу кухни — заказ остаётся в отчёте, даже когда официант
  отметил его «подано»
- `GET /api/owner/orders` — список заказов с типом (в зале / с собой) и способом оплаты
- `PUT /api/owner/menu/:id` — изменить блюдо, цену, наличие, назначить блюдо дня
- `POST /api/owner/settings/commission-rate` — поменять процент комиссии на лету

## Демо-режим (показ без сервера)

Все три HTML-файла умеют работать **без бэкенда**: если сервер недоступен, приложение
само переключается на встроенные демо-данные и наверху появляется красная плашка
«ДЕМО-РЕЖИМ». Все экраны и кнопки при этом кликаются — можно показать сервис
менеджеру кафе с ноутбука или телефона, ничего не разворачивая.

Как только бэкенд запущен и `API_BASE` указывает на него, приложения автоматически
работают с реальными данными, и плашка не появляется.

## Запуск локально

```bash
npm install
cp .env.example .env      # впишите свои OWNER_API_KEY и STAFF_API_KEY
npm run seed               # заполнит базу вашим текущим меню (салаты + напитки)
npm start                  # сервер поднимется на http://localhost:3000
```

Проверить, что всё работает:

```bash
curl http://localhost:3000/api/health
curl http://localhost:3000/api/menu
```

Открыть в браузере (на этом же компьютере):

- http://localhost:3000/ — меню гостя
- http://localhost:3000/staff — официант (ключ по умолчанию из `.env.example`: `change-me-staff-key`)
- http://localhost:3000/owner — владелец (ключ по умолчанию: `change-me-owner-key`)

## Один деплой — все три приложения на одном адресе

Раньше бэкенд и три HTML-файла нужно было размещать отдельно, и в каждом файле
вручную менять адрес сервера. Теперь бэкенд сам раздаёт все три страницы —
после деплоя у вас будет **один адрес**, и:

- `https://ваш-адрес.onrender.com/` — меню для гостей (сюда ведёт NFC/QR на столе)
- `https://ваш-адрес.onrender.com/staff` — экран официанта/кухни
- `https://ваш-адрес.onrender.com/owner` — панель владельца

Файлы для гостя, официанта и владельца лежат в папке `public/` и находятся автоматически —
их не нужно заливать отдельно, они уже часть этого проекта.

## Как задеплоить бесплатно (Render.com) — шаг за шагом

**Шаг 1. Код должен оказаться на GitHub.**
Render разворачивает проект из GitHub-репозитория, поэтому сначала нужно туда
загрузить эту папку целиком (`rahat-backend`, включая папку `public/`). Можно
сделать репозиторий приватным — Render всё равно сможет его увидеть, если вы
разрешите доступ при подключении.

**Шаг 2. Создать сервис на Render.**
На render.com → **New → Web Service** → выбираете свой репозиторий.
Это говорит Render: «вот код, разверни его как постоянно работающий сервер»
(в отличие от статического сайта — нам нужен именно сервер, потому что есть база
данных и приём заказов).

**Шаг 3. Настройки сборки.**
- Build command: `npm install` — это команда, которая ставит зависимости
  (Express, SQLite и т.д.) перед первым запуском
- Start command: `npm start` — так Render будет запускать сервер каждый раз

**Шаг 4. Секретные ключи.**
В разделе Environment добавьте две переменные:
- `OWNER_API_KEY` — придумайте длинную случайную строку, это ваш личный ключ
- `STAFF_API_KEY` — отдельная строка для официантов

Это те же ключи, что вы будете вводить в приложении при подключении — без них
никто посторонний не попадёт в панель владельца или официанта, только в
обычное гостевое меню (оно и должно быть открыто всем).

**Шаг 5. Заполнить базу меню один раз.**
После первого успешного деплоя нужно один раз выполнить `npm run seed` —
это кладёт в базу данных ваши текущие блюда (салаты, напитки), чтобы гости
сразу видели меню, а не пустую страницу. Сделать это можно через встроенную
консоль (Shell) в панели Render — там просто вводите `npm run seed` и жмёте Enter.
Дальше это не понадобится — новые блюда вы уже добавляете через приложение
официанта/владельца, а не через эту команду.

**Шаг 6. Получить адрес.**
Render выдаст адрес вида `https://rahat-backend.onrender.com`. Это и есть тот
самый единственный адрес — просто добавляйте `/staff` или `/owner` в конце
для остальных двух приложений.

**Шаг 7. Обновить печатные материалы.**
На NFC-карточке/QR-коде на столах должна быть ссылка именно на этот адрес
(корневой, без `/staff` и `/owner`) — если печатали карточки раньше с
демонстрационной ссылкой, перегенерируйте QR с реальным адресом.

Render бесплатного тарифа «засыпает» после 15 минут без запросов, и первый
визит после сна грузится ~20-30 секунд — для пилота на одно кафе это не
критично, но официанту стоит об этом знать (если экран долго не трогали).

## Что понадобится ввести в приложениях

После деплоя ничего в самих HTML-файлах менять не нужно — адрес сервера
подхватывается автоматически (страница сама знает, с какого адреса её открыли).
Единственное, что вводится вручную — это ключи доступа:

- Гость — открывает `/` — ничего вводить не нужно, доступ открыт всем
- Официант — открывает `/staff` → вводит `STAFF_API_KEY`
- Владелец — открывает `/owner` → вводит `OWNER_API_KEY`

## Приём оплаты СБП — как включить по-настоящему

По умолчанию (пока в `.env` нет ключей ЮKassa) оплата СБП работает в демо-режиме —
гость видит красивую анимацию, но реальные деньги не списываются. Это специально,
чтобы можно было показывать и тестировать сервис до того, как оформлен эквайринг.

**Почему именно ЮKassa, а не конкретный банк напрямую:** у каждого банка (Т-Банк,
Сбер, Альфа) свой отдельный API, и выбор банка — решение владельца кафе. ЮKassa —
агрегатор: один и тот же код работает независимо от того, каким банком в итоге
пользуется владелец, плюс уже решает вопрос чеков по 54-ФЗ.

**Как включить:**

1. Владелец регистрируется на [yookassa.ru](https://yookassa.ru) как ИП или
   самозанятый (документы, проверка — обычно 1–3 дня)
2. В личном кабинете ЮKassa: Настройки → Магазин → берёте `shopId` и `secretKey`
3. Там же: Интеграция → HTTP-уведомления → включаете и указываете адрес:
   `https://ваш-адрес.onrender.com/api/webhooks/yookassa`
4. Добавляете в `.env` (или в Environment на Render):
   ```
   YOOKASSA_SHOP_ID=...
   YOOKASSA_SECRET_KEY=...
   ```
5. Перезапускаете сервер — всё, с этого момента оплата СБП настоящая

**Как это работает технически (если интересно):**
- `POST /api/orders` при `paymentMethod: "sbp"` создаёт платёж в ЮKassa и возвращает
  `confirmationUrl` — гостя перенаправляет туда браузер, там ЮKassa сама показывает
  список банков (на телефоне) или QR (на компьютере)
- После оплаты ЮKassa стучится на `/api/webhooks/yookassa` — сервер **не верит**
  содержимому уведомления напрямую, а перепроверяет статус платежа напрямую через
  API ЮKassa, и только тогда помечает заказ оплаченным (это защита от поддельных
  уведомлений)
- Старый ручной эндпоинт `confirm-payment` автоматически отключается, как только
  ЮKassa настроена — раньше он был нужен только для демо-тестов

## Что обязательно нужно доделать перед реальными деньгами

- **HTTPS обязателен** — Render даёт его автоматически, так что при деплое туда
  это уже решено
- **Резервное копирование базы** — SQLite-файл стоит периодически скачивать/бэкапить,
  особенно на бесплатных тарифах, где диск не всегда постоянный
- **Загруженные фото хранятся на диске рядом с сервером** (папка `uploads/`) — на
  бесплатных тарифах хостинга (в т.ч. Render Free) диск может очищаться при
  redeploy/засыпании. Для долгосрочного хранения фото на проде лучше переехать на
  внешнее хранилище (S3-совместимое, Cloudinary и т.п.) — сама механика загрузки
  (эндпоинт принимает файл, возвращает ссылку) при этом не меняется, меняется только
  то, куда физически кладётся файл внутри `/api/staff/upload`
- Сейчас по одному секретному ключу на роль — нормально для одного кафе, но при
  росте (несколько кафе, несколько сотрудников с личными доступами) лучше сделать
  нормальную систему логина с именными аккаунтами
